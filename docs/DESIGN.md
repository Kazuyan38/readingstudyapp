## 1. コンセプト

読書は「読んだ量」ではなく「残った量」で決まる。本アプリは、読書メモを **要点カード** に凝縮し、エビングハウスの忘却曲線に沿って復習を出し分けることで、読んだ内容を確実に長期記憶に定着させる。

体験の中心にあるのは 3 つのループ:

```
① 記録 ──→ ② 蒸留 ──→ ③ 定着
 本を登録    メモを要点     忘却曲線に沿って
 メモを書く   カードに凝縮    復習・想起する
   ↑                          │
   └──────────────────────────┘
        検索・再発見でループが回り続ける
```

### 設計原則

| 原則 | 意味 |
| --- | --- |
| 摩擦ゼロの記録 | メモを書くのに 3 クリック以上かけさせない。思考を止めない |
| 蒸留を強制しない | 生メモはそのまま残す。カード化は任意・後追いでよい |
| 復習は「今日の分だけ」 | 未消化の山を見せない。今日やるべき枚数だけを提示する |
| 記憶を可視化する | 「何％覚えているか」を光の強さとして常に見せる |
| どの端末でも同じ状態 | PC で作ったカードがスマホで復習できる。同期は意識させない |
| データは自分のもの | オフラインで完結し、サーバーには読めない形で置く。いつでも JSON で持ち出せる |

## 2. スコープ

### 想定利用者

- **自分一人用 / アカウント登録なし**。他人とデータを共有する機能は作らない。
- **複数端末で使う**。PC で記録し、スマホで復習する、が日常の使い方。
- スマホでは **PWA としてホーム画面に追加**して使う（iOS ではホーム画面アプリはストレージの 7 日削除ルールの対象外になる — WebKit 公式。§11）。
- オフラインで完全に動作し、オンラインになったら自動で同期する。
- アプリ本体は公開 URL に置かれ誰でも開けるが、開いた人に見えるのは各自のブラウザ内データだけ。自分のデータはサーバー上でも暗号文のみ（§6.2）。

### やること（MVP に含む）

- 蔵書の登録・管理（ISBN 検索による自動入力を含む）
- 読書メモ / ハイライト / 引用の記録
- メモから要点カードへの蒸留
- 忘却曲線ベースの復習スケジューリングと復習セッション
- **端末間同期**（同期キーによるペアリング、オフライン対応、End-to-End 暗号化）
- 全文検索（日本語対応）
- 統計・記憶保持率の可視化
- JSON エクスポート / インポート

### やらないこと（意図的な非スコープ）

- メール / パスワードによるユーザー登録、ソーシャル機能、他人との共有
- 電子書籍リーダー機能（本文の閲覧そのものは扱わない）
- 課金・サブスクリプション
- ネイティブアプリ（PWA で代替）
- プッシュ通知による復習リマインド（GitHub Pages にプッシュサーバーは置けず、iOS の Web Push はホーム画面追加＋プッシュサーバー必須。復習キューはアプリを開いたときに提示する）

> **「アカウントなし」と「同期」の両立**: 一般的なアカウント登録の代わりに、**1 本の同期キー（パスフレーズ）**で端末を紐付ける。詳細は §6。

## 3. 忘却曲線エンジン（本アプリの心臓部）

### 3.1 理論的背景

エビングハウスの節約率曲線は、記憶保持率 R が時間 t とともに指数的に減衰することを示す。

```
R(t) = e^(−t / S)      R: 保持率, t: 経過時間, S: 記憶の安定度
```

重要なのは **S（安定度）は復習のたびに増大する** という点。つまり復習間隔は等間隔ではなく、指数的に伸ばすのが最も効率的になる。

### 3.2 採用アルゴリズム: ハイブリッド SM-2

純粋な固定ステップ（20分 / 1日 / 3日 / 7日 / …）は理論に忠実だが、カードごとの難易度差を吸収できない。逆に FSRS は高精度だが個人利用にはパラメータ最適化が過剰。

**採用**: 学習初期は固定ステップ、定着後は SM-2 の可変間隔に移行するハイブリッド方式。

#### 学習ステップ（新規カード）

```
作成直後 → 10分後 → 翌日 → 3日後 → [卒業] → SM-2 へ
```

#### SM-2 本体（卒業後）

復習時の自己評価を 4 段階で受け取り、内部的に quality `q` へマップする。

| ボタン | 意味 | q |
| --- | --- | --- |
| もう一度 | 思い出せなかった | 1 |
| むずかしい | 苦労して思い出した | 3 |
| ふつう | 思い出せた | 4 |
| かんたん | 即答できた | 5 |

```ts
// EF: 難易度係数（初期 2.5, 下限 1.3）
// n : 連続正解回数
// I : 次回までの間隔（日）

if (q >= 3) {
  if (n === 0)      I = 1
  else if (n === 1) I = 6
  else              I = Math.round(I_prev * EF)
  n = n + 1
} else {
  n = 0
  I = 1              // 翌日に再出題
}

EF = Math.max(1.3, EF + (0.1 - (5 - q) * (0.08 + (5 - q) * 0.02)))

// 同じ日に大量に集中しないよう ±5% のジッタを乗せる
dueAt = now + I * (1 + jitter(-0.05, 0.05)) days
```

「かんたん」を選んだ場合は追加で `I *= 1.3`（easy bonus）。

### 3.3 記憶保持率の推定（UI 表示用）

各カードについて、次回復習予定日 `I` でちょうど 90% の保持率になるようモデル化する。

```
R(t) = 0.9 ^ (t / I)      t: 前回復習からの経過日数
```

- `t = 0` → 100%
- `t = I`（期日当日）→ 90%
- `t = 2I`（1 週間放置）→ 81%

この `R` を **カードの発光量・不透明度** に直結させる。覚えているカードは澄んで輝き、忘れかけたカードは霞んで沈む。ロジックがそのまま意匠になる。

### 3.4 一日の負荷制御

- 1 日あたりの新規カード上限（既定 10 枚）と復習上限（既定 60 枚）を設定可能。
- 上限を超えた分は翌日以降へ自動的に繰り延べ、期日超過の古いものから優先。
- 「今日はここまで」を明示し、未消化の総数はダッシュボードに出さない（罪悪感を作らない）。

### 同期のための共通フィールド

`Book` / `Note` / `InsightCard` / `Tag` / `ReviewLog` の全テーブルが以下を持つ。

| フィールド | 型 | 役割 |
| --- | --- | --- |
| `id` | string (uuid v7) | **端末側で採番する**。サーバー採番だとオフライン作成ができない。v7 は時系列順で索引効率もよい |
| `updatedAt` | number (epoch ms) | 競合解決の基準。端末時計のズレ対策として §6.4 を参照 |
| `deletedAt` | number \| null | **物理削除しない**。削除は tombstone として同期する（消したのに他端末から復活する事故を防ぐ） |
| `syncedAt` | number \| null | 最後にサーバーへ送れた時刻。`null` または `< updatedAt` なら未同期＝送信対象 |

`ReviewLog` だけは **append-only** で `updatedAt` の更新も削除も起きない。この性質が §6.3 の競合解決を成立させる。

## 5. 技術スタック

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| フレームワーク | **Vite + React 19 + TypeScript + React Router** | 全画面が IndexedDB からのクライアント描画でサーバー機能を一切使わないため、純粋な SPA が最適。`/books/:id` の動的 URL をそのまま保てる（Next.js の静的エクスポートは実行時 ID の動的ルートを出力できない — 検証済み・2026-08） |
| スタイル | **Tailwind CSS v4** | CSS 変数ベースのテーマ切替がしやすく、ガラス質の意匠をトークン化できる |
| モーション | **Motion（旧 Framer Motion）** | レイアウトアニメーションと SVG パス描画が両方必要 |
| ローカル永続化 | **IndexedDB + Dexie 5** | オフラインでの読み書きの源。UI は常にローカルだけを見るので、同期の遅延が体感に出ない |
| 同期バックエンド | **Cloudflare Workers + D1（SQLite）** | GitHub Pages にはサーバーコードも秘密情報も置けないため、同期エンドポイントは外部に必須。無料枠（10万リクエスト/日・D1 5GB）はクレカ不要で、超過時は課金でなく**エラー停止**（§6.5） |
| 暗号化 | **Web Crypto API（PBKDF2 + HKDF + AES-GCM）** | 同期キーから鍵を導出し、サーバーには暗号文だけを置く。追加ライブラリ不要（Argon2 は Web Crypto 未搭載。WASM 版は GitHub Pages で COOP/COEP ヘッダを設定できずシングルスレッドになるため利得がなく見送り） |
| 全文検索 | **MiniSearch + TinySegmenter** | クライアント完結。日本語は形態素分割 + bigram フォールバックで補う。**暗号化と両立するのはこの構成だから**（§6.2） |
| 書誌データ | **openBD → NDL サーチ → 楽天ブックス → Google Books** の多段 | 全てブラウザから直接呼べる（CORS 実地確認済み・2026-08）。openBD の表紙・内容紹介は 2023-06 以降 版元ドットコム会員社のみに縮小しており、多段フォールバックが必須（§11） |
| グラフ | **自作 SVG コンポーネント** | 忘却曲線・ヒートマップとも意匠の一部。汎用ライブラリでは絵が揃わない |
| 配信 | **GitHub Pages + GitHub Actions** + **PWA（vite-plugin-pwa）** | main へ push すれば自動デプロイ（§5.2）。PWA 化はホーム画面追加・オフライン動作のため必須 |

### 5.1 永続化の設計上の判断

「オフラインで即座に動く」と「端末間で同期する」を両立させるため、**ローカルファースト + バックグラウンド同期**を採る。サーバーを正とする設計にしないのは、電車の中や機内で復習できなくなるため。

```text
    UI （Dexie しか知らない）
      │
      ▼
  repository.ts  ─── 書き込みのたびに outbox へ積む
      │
      ▼
   Dexie / IndexedDB   ← 常にここが読み取りの唯一の源（＝表示は必ず即時）
      │
      ▼
   sync engine   ─── 暗号化 → push → pull → 復号 → マージ
      │
      ▼  クロスオリジン fetch
  POST https://<sync-worker>.workers.dev/sync  →  D1
```

- **UI は Dexie しか知らない**。ネットワークの有無、同期の成否、競合の解決は全て同期エンジンの内側に隠す。
- リポジトリ層（`lib/db/repository.ts`）が唯一の永続化 API。バックエンドを差し替えても UI は無変更。
- IndexedDB が消えても、サーバーから全件 pull し直せば復元できる（**同期がバックアップを兼ねる**）。
- ただしサーバー側の消失・アカウント停止に備え、JSON エクスポートは引き続き必須機能とする（既定の保存先として OneDrive フォルダを案内）。
- 同期エンドポイントの URL はビルド時定数（`VITE_SYNC_ENDPOINT`）としてバンドルに埋め込む。URL は秘密ではない（認証は spaceId が担う。§6.1）。

### 5.2 配信 — GitHub Pages

配信は GitHub Actions によるデプロイフローに固定する（Settings → Pages → Source: **GitHub Actions**）。

```yaml
# .github/workflows/deploy.yml の骨子
on: { push: { branches: [main] } }
jobs:
  deploy:
    steps:
      - checkout → npm ci → npm run build        # vite build
      - run: cp dist/index.html dist/404.html    # ★ SPA フォールバック
      - actions/upload-pages-artifact (dist/)
      - actions/deploy-pages
```

| 決定事項 | 内容 |
| --- | --- |
| `vite.config.ts` | `base: '/readingstudyapp/'`（プロジェクトサイトはサブパス配信のため必須） |
| SPA フォールバック | GitHub Pages は SPA を知らないので、`/books/xxx` への直リンクは 404 になる。`index.html` を `404.html` としてコピーしておくと、GitHub Pages が 404 時にこれを返し、React Router が URL を復元する。**HTTP ステータスは 404 のまま**だが（Pages はヘッダもリダイレクトも設定不可）、検索エンジンに載せる必要のない個人用 PWA では実害がない。PWA インストール後は SW のナビゲーションフォールバックが引き継ぎ、この経路自体を通らなくなる |
| Jekyll | Actions デプロイでは Jekyll は一切走らないため `.nojekyll` は不要（ブランチデプロイに切り替える場合のみ必須になる — 罠として明記） |
| リポジトリ | 公開のまま維持（無料枠の Pages は公開リポジトリが条件）。コードも単語リストも salt も公開になるが、設計上それで安全（§6.1） |
| 制限 | サイト 1GB・帯域 100GB/月（ソフト制限）。静的アセットのみなので遠く及ばない |

## 6. 同期アーキテクチャ

### 6.1 端末のペアリング —「同期キー」

アカウント登録の代わりに、**1 本のパスフレーズ**で端末を束ねる。

1. 最初の端末で「同期を有効にする」を押すと、**6 語のパスフレーズ**を生成する（例: `藍色 / 灯台 / 余白 / 螺旋 / 雪解け / 手紙`）。**2048 語以上の日本語単語リスト**から CSPRNG で選ぶ（6 語で 66 bit — BIP39 と同等）。暗記も転記もしやすく、総当たりには十分な強度がある。
2. 2 台目では、そのパスフレーズを入力するか、1 台目が表示する **QR コード**を読む。
3. 以後、パスフレーズは端末内（IndexedDB）に保持され、再入力は不要。

パスフレーズから、PBKDF2（SHA-256 / 600,000 回）で 2 つの値を導出する。

```ts
// Web Worker 内で実行（中位スマホで 0.5〜2 秒。端末につき 1 回だけなので許容）
const material = PBKDF2(passphrase, salt: "readingstudyapp/v1", 600_000)

spaceId = HKDF(material, info: "readingstudyapp/id")    // サーバーへ送る。データの置き場所を示すだけ
dataKey = HKDF(material, info: "readingstudyapp/data")  // ★ 端末から絶対に出さない。暗号化に使う
```

2 つの値はどちらも HKDF の `info` 文字列で用途分離して導出する（アドホックな連結ハッシュを混ぜない）。`spaceId` は「どの棚か」を示すラベルにすぎず、これだけでは中身を読めない。

> **公開リポジトリとの両立**: リポジトリ公開により単語リストも固定 salt も全世界に見える。それでも安全なのは、パスフレーズが人間の選ぶ弱い文字列ではなく CSPRNG 生成（66 bit + PBKDF2 の作業量 ≈ 実効 2^85）だから。強度の根拠がコードの秘匿ではなくエントロピーにある、という前提を崩さないこと（単語リストを小さくしない）。

### 6.2 End-to-End 暗号化

公開 URL 上に読書メモを平文で置きたくないため、**サーバーには暗号文しか渡さない**。

```
サーバーが保持するレコード:
{
  spaceId:   "a3f1…",        ← 誰の棚か（ハッシュ）
  entityId:  "018f-…",       ← uuid v7
  entityType:"insight_card",
  updatedAt: 1755400000000,  ← 競合解決に必要なので平文
  deletedAt: null,           ← 同上
  ciphertext:"<AES-GCM>",    ← 本文・タイトル・メモ … 全て
  iv:        "<12 bytes>"
}
```

平文で置くのは同期の制御に最低限必要な 4 つだけ。本文・書名・メモ・カードの内容は全て `ciphertext` の中に入る。

**この方式が成立するのは、検索が元々クライアント側（MiniSearch）だから**である。サーバーで全文検索する設計だったなら暗号化は不可能だった。§5 の技術選定と §6 の暗号化は独立した判断ではなく、セットで初めて成り立つ。

| トレードオフ | 内容 |
| --- | --- |
| 得るもの | サーバーが漏れても中身は読めない。運用者（自分）ですら DB を覗けない |
| 失うもの | **パスフレーズを忘れると復号不能＝全損**。サーバー側での検索・集計・移行スクリプトが一切書けない |

対策として、初回セットアップ時に **パスフレーズの控えを必ず取らせる**（コピー / 印刷 / ダウンロードのいずれかを実行するまで次へ進ませない）。JSON エクスポートが必須機能である理由もここにある。

### 6.3 差分同期プロトコル

エンドポイントは 1 本のみ。push と pull を 1 往復にまとめる。フロントが `kazuyan38.github.io`、ワーカーが `*.workers.dev` とオリジンが分かれるため、必ずクロスオリジンになる。

```text
POST https://readingstudyapp-sync.<account>.workers.dev/sync
Authorization: Bearer <spaceId>

Request  { since: 1755400000000, changes: [ …未同期レコード… ] }
Response { serverTime: …, changes: [ …since 以降の他端末の変更… ], hasMore: false }
```

**CORS**: `Authorization` ヘッダ付き POST は必ずプリフライトされるため、ワーカーは OPTIONS に応答し、`Access-Control-Allow-Origin: https://kazuyan38.github.io` / `Allow-Methods: POST, OPTIONS` / `Allow-Headers: Authorization, Content-Type` / `Max-Age: 86400` を返す（実装 15 行程度）。なお CORS はセキュリティ境界ではない（curl は無視できる）— 防御は次項が担う。

**公開エンドポイントの防御（全て無料）**

| 層 | 内容 |
| --- | --- |
| ① spaceId 許可リスト | `SHA-256(spaceId)` をワーカーのシークレット（`wrangler secret put ALLOWED_SPACE_HASH`）に置き、一致しない spaceId は 403。一人用アプリだからこそ使える最強の一手で、**未知の spaceId によるストレージ洪水が原理的に不可能になる**。新しいパスフレーズを作り直すときだけ secret を更新する |
| ② サイズ上限 | D1 に触る前に、ボディ 1MB / レコード 64KB を超えるリクエストを拒否 |
| ③ レート制限 | Workers のレート制限バインディング（無料・GA）で IP あたり 60 回/分 |

**手順**

1. **push** — ローカルの `syncedAt < updatedAt` なレコードを暗号化して送る。1 回あたり最大 200 件、超える分は `hasMore` でページングする。
2. **pull** — 前回の `serverTime`（＝`since`）以降に他端末が書いたレコードを受け取る。
3. **マージ** — 種別ごとに以下の規則で適用する。
4. `since` を応答の `serverTime` に更新して保存する。

**競合解決の規則**

| 対象 | 規則 |
| --- | --- |
| `ReviewLog` | **和集合**（`id` で重複排除）。append-only なので競合が原理的に起きない |
| 本文・書名・メモなど内容フィールド | **Last-Write-Wins**（`updatedAt` が新しい方を採る）。一人で使う以上、同じメモを 2 台で同時編集することはまずない |
| 削除 | `deletedAt` が立っている側を優先。**削除は編集に勝つ** |
| `InsightCard` の SRS 状態 | ★ **LWW を使わず、マージ後の `ReviewLog` から再計算する**（下記） |

**SRS 状態だけを特別扱いする理由**

PC で復習してから、同期前にスマホでも同じカードを復習した場合、LWW だと片方の復習が「なかったこと」になり、間隔が誤って伸びる。忘却曲線アプリとしてこれは最も起きてはいけない壊れ方である。

`ReviewLog` は和集合で必ず両方揃うので、**両端末の履歴を時系列に並べ、`scheduler.ts` に順に流し直して状態を作る**。スケジューラを純粋関数として書く（§9）と決めていたのは、この再計算のためでもある。

```ts
// 競合したカードの SRS 状態を、履歴の再生で確定させる
const logs = mergedLogs.filter(l => l.cardId === card.id)
                       .sort((a, b) => a.reviewedAt - b.reviewedAt)
const srs = logs.reduce(applyReview, initialSrsState(card))
```

副次的な効果として、**将来 SM-2 から FSRS へ乗り換える際も同じ再生処理がそのまま使える**（§4 で ReviewLog を不変ログと決めた狙いが、ここで同期と移行の両方に効いてくる）。

### 6.4 同期のタイミングと体感

| 契機 | 動作 |
| --- | --- |
| 書き込みのたび | 3 秒デバウンスして push |
| アプリ起動時 / タブ復帰時 | 即座に pull |
| 復習セッション終了時 | 確実に push（端末をまたぐ最も重要な瞬間） |
| オンライン復帰時 | `outbox` を順に送信 |
| 定期 | 5 分ごと |

- **オフライン時**: 書き込みはローカルに残り、`outbox` に積まれる。UI 上は何も変わらない。ヘッダーに小さな「未同期 3 件」の表示だけを出す。
- **端末時計のズレ**: `updatedAt` に端末時計をそのまま使うと、時計が狂った端末の書き込みが永遠に勝ち続ける事故が起きる。応答の `serverTime` とローカル時刻の差分をオフセットとして保持し、補正した値を `updatedAt` に書く。
- **表紙画像**: Blob は同期しない（容量が支配的になるため）。`coverUrl` だけを同期し、表示は各端末が `<img>` で直接参照する。Blob キャッシュは CORS を返す経路から取れた場合のみのベストエフォート（§11）。

### 6.5 バックエンドの選択

前提: **公開静的サイトには秘密（DB トークン）を置く場所が存在しない**。DB がどこにあろうと、トークンを保持する薄いサーバーが 1 枚必須になる — これが比較の出発点。

| 候補 | 評価 |
| --- | --- |
| **Cloudflare Workers + D1** ★採用 | トークンを保持するワーカーがどのみち必須なら、D1（SQLite）も同居させて 1 ベンダーで完結させるのが最小構成。無料枠（10万リクエスト/日・D1 5GB・書き込み 10万行/日）はクレカ不要で、**超過は課金でなくエラー停止** — 悪用されても請求が来ない。レート制限バインディングも無料 |
| Turso（旧採用） | 無料枠は健在だが、トークンの権限は**テーブル単位まで**で行単位に絞れない（実地確認済み）。ブラウザ直叩きは公開バンドルへのトークン埋め込みになり、全行の読み取り・上書き・全削除を誰にでも許すため**不可**。ワーカーの裏に置くなら D1 に対する利点が消える |
| Supabase | RLS + anon キーで理論上サーバーレス直叩きも組めるが、**7 日間無アクセスでプロジェクトが休止**し手動復旧が要る。1 週間の旅行で同期が黙って死ぬのは日用アプリとして不適 |
| Vercel Functions | フロントを Pages に置いて API だけ Vercel は本末転倒（それなら全体を Vercel に置く）。GitHub Pages の決定と矛盾 |
| GitHub リポジトリを DB 代わりに | 追加サービス不要で魅力的だが、コミット競合とレート制限の処理が同期エンジンより複雑になる。不採用 |

D1 は SQLite そのものなので、スキーマは設計済みのものがそのまま使える。

```sql
CREATE TABLE records (
  space_id    TEXT NOT NULL,
  entity_id   TEXT NOT NULL,
  entity_type TEXT NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER,
  ciphertext  BLOB NOT NULL,
  iv          BLOB NOT NULL,
  PRIMARY KEY (space_id, entity_id)
);
CREATE INDEX idx_pull ON records (space_id, updated_at);
```

サーバーは中身を解釈しない。**同期の賢さは全てクライアントに置く**ことで、バックエンドの差し替えを最後まで安価に保つ。

```
│   ▁▂▄▆█▆▄▂▁  今後 30 日の復習予定             │
└──────────────────────────────────────────────┘
```

### 7.2 復習セッション

集中を切らさないため、ナビゲーションを全て隠したフルスクリーン。

1. `front`（問い）のみをガラスカードに表示
2. スペースキー / タップで `back` が **溶けるように** 現れる
3. 4 段階評価（`1` `2` `3` `4` キーでも操作可）
4. カードが光の粒になって散り、次のカードが浮かび上がる
5. 完了時は「今日はここまで」の静かな画面。翌日の枚数だけを予告

出典の本と該当メモへは、カード上の控えめなリンクから常に辿れる（文脈を失わせない）。

### 7.3 蒸留フロー

`distilled: false` のメモを 1 件ずつ提示し、以下の 3 択で捌く。

- **カードにする** → `front` / `back` 編集画面へ（`back` の初期値はメモ本文）
- **今はしない** → スキップ（次回また出る）
- **カード化しない** → `distilled: true` にして以後出さない（メモ自体は残る）

複数のメモを選択して 1 枚のカードに統合できることが、単なるメモアプリとの決定的な差になる。

## 8. ビジュアルデザイン

**目指す形容**: 透き通った / 静謐 / 芸術的 / 上質。装飾的ではなく、素材の質感で美しさを出す。

### 8.1 コンセプト —「記憶の水面」

記憶を、光を透かす水面として表現する。ガラス質のカードが深い藍の霧の上に浮かび、保持率に応じて透明度と発光が変わる。時間が経ったカードは水底に沈むように霞み、復習すると再び水面へ浮上して輝く。

### 8.2 カラートークン

```css
:root {
  /* Light — 霧氷 */
  --bg-base:      #f4f6fb;
  --bg-mesh-a:    #dbe4ff;
  --bg-mesh-b:    #e7dcf5;
  --bg-mesh-c:    #d6efee;
  --glass-fill:   rgb(255 255 255 / 0.55);
  --glass-stroke: rgb(255 255 255 / 0.75);
  --text-primary: #14192b;
  --text-muted:   #5b6480;
  --accent:       #4f6bff;   /* 藍 — 主要アクション */
  --accent-warm:  #c9a227;   /* 金 — 定着・達成 */
}

:root:not([data-theme="light"]) {
  /* Dark — 深海（既定） */
  --bg-base:      #070b16;
  --bg-mesh-a:    #17225c;
  --bg-mesh-b:    #3a1d5e;
  --bg-mesh-c:    #0d3f4a;
  --glass-fill:   rgb(255 255 255 / 0.06);
  --glass-stroke: rgb(255 255 255 / 0.14);
  --text-primary: #eef1f8;
  --text-muted:   #98a2bd;
  --accent:       #7e9bff;
  --accent-warm:  #e8c66a;
}
```

ダークを既定とする。読書アプリの利用時間帯（夜）と、ガラス質の表現がダーク背景で最も映えることの両方から。

### 8.3 質感

**背景**: 3 点のラジアルグラデーションで作るメッシュを、60 秒周期で極めてゆっくり移動させる。上に微細なノイズテクスチャ（`opacity: 0.03`）を重ね、デジタル特有の平坦さを消す。

**ガラス面**:
```css
.glass {
  background: var(--glass-fill);
  backdrop-filter: blur(24px) saturate(1.4);
  border: 1px solid var(--glass-stroke);
  border-radius: 20px;
  box-shadow:
    0 8px 32px rgb(0 0 0 / 0.25),
    inset 0 1px 0 rgb(255 255 255 / 0.2);  /* 上端の光の縁 */
}
```

`inset` の白い 1px が、ガラスの厚みと縁の反射を作る。この一行の有無で質感が決定的に変わる。

**保持率の表現**: カードの `opacity` と発光を `R(t)` に連動させる。

| R | 見え方 |
| --- | --- |
| 100–90% | 澄んで、縁が淡く光る |
| 90–70% | 通常 |
| 70–50% | わずかに霞む |
| < 50% | 深く沈み、輪郭がぼやける（要復習のサイン） |

### 8.4 タイポグラフィ

| 用途 | 書体 |
| --- | --- |
| 見出し・引用 | **Shippori Mincho**（和） / **EB Garamond**（欧） — 本の品格 |
| 本文・UI | **Noto Sans JP** / **Inter** — 可読性 |
| 数値・日付 | **Inter** tabular-nums — 統計の桁揃え |

本文行長は最大 68 文字、行間 1.9。読書アプリである以上、**文章そのものが最も美しく見えること**が最優先。

フォントは Fontsource パッケージでビルド時に同梱し自己ホストする（実行時に Google Fonts へのリクエストなし＝オフラインでも同じ見た目。日本語フォントは unicode-range サブセットで分割配信されるため初期ロードも重くならない）。

### 8.5 モーション

| 対象 | 動き | 時間 |
| --- | --- | --- |
| 解答の表示 | ブラー 12px → 0 + フェード | 420ms |
| カードの完了 | 上へ 8px + フェードアウト | 320ms |
| ページ遷移 | クロスフェード（スライドしない） | 280ms |
| 保持率リング | パスを 0 → 値へ描画 | 900ms, ease-out |
| 背景メッシュ | 位相の連続移動 | 60s ループ |

イージングは全て `cubic-bezier(0.22, 1, 0.36, 1)`。跳ねさせない。静けさを壊すものは入れない。

`prefers-reduced-motion: reduce` の場合、背景アニメーションと装飾的モーションを全て停止し、状態変化のみ即時反映する。

| **2. 定着** ★ | SRS エンジン、蒸留フロー、復習セッション | カードを作り、翌日に正しく出題される |
| **3. 同期** ★ | 鍵導出・暗号化、**同期ワーカー（Workers + D1）のデプロイ**、マージとログ再生、ペアリング UI | PC で作ったカードをスマホで復習でき、両方で復習しても間隔が壊れない |
| **4. 検索** | MiniSearch インデックス、日本語トークナイズ、横断検索 | 書いたメモを日本語で引ける |
| **5. 可視化** | 忘却曲線グラフ、ヒートマップ、保持率オーブ | 統計画面が単体で見て美しい |
| **6. 意匠** | 背景メッシュ、モーション、reduced-motion 対応 | 全画面がコンセプトどおりの質感になる |
| **7. 堅牢化** | エクスポート / インポート、PWA（vite-plugin-pwa・`storage.persist()`・iOS ホーム画面追加の案内）、オフライン検証 | データを失う経路がない。機内モードで復習が一周できる |

Phase 2 と 3 が難所であり、かつ本アプリの価値そのもの。Phase 1 は最小限で通過して 2・3 に時間を割く。デプロイパイプラインを Phase 0 に置くのは意図的 — サブパス配信（`/readingstudyapp/`）起因のアセット・ルーティング不具合は、後回しにすると PWA 期まで潜伏するため。

> **Phase 1 での先行対応（重要）**: 同期エンジン自体は Phase 3 だが、**§4 の共通同期フィールド（`updatedAt` / `deletedAt` / `syncedAt`、uuid v7、論理削除）は Phase 1 の時点でスキーマに入れておく**。実データが溜まってから論理削除へ移行すると、削除済みレコードの履歴が存在せず、同期開始時に消したはずの本が復活する。後から足せない類の設計であるため、ここだけは前倒しする。

## 11. 主要な技術課題と対処

| 課題 | 対処 |
| --- | --- |
| **日本語の全文検索** | MiniSearch は空白区切り前提。TinySegmenter で分かち書きし、加えて bigram インデックスを併用して分割ミスを吸収する |
| **IndexedDB のデータ消失** | サーバーから全件 pull し直して復元できる（同期がバックアップを兼ねる）。加えて月 1 回の JSON エクスポート促しを残す |
| **パスフレーズの紛失＝全損** | E2E 暗号化の代償として避けられない。初回に控えを取るまでセットアップを完了させない導線でしか防げないと割り切る。JSON エクスポート（平文）が最後の砦 |
| **2 端末で同じカードを復習** | SRS 状態を LWW で上書きせず、和集合した `ReviewLog` を `scheduler` に流し直して再計算する（§6.3）。忘却曲線アプリで最も許容できない壊れ方なので、ここだけ特別扱いする |
| **端末時計のズレによる誤った勝敗** | サーバー時刻との差分をオフセットとして保持し、補正済みの値を `updatedAt` に書く（§6.4） |
| **削除したデータの復活** | 物理削除を禁止し、`deletedAt` の tombstone を同期する。削除は編集に勝つ規則を貫く |
| **同期の失敗がユーザーを不安にさせる** | 失敗をエラーとして見せない。ローカルには必ず保存されているので、「未同期 N 件」の静かな表示に留め、復帰時に自動で送る |
| **backdrop-filter の描画負荷** | ガラス面の同時表示数を 1 画面 12 枚程度に抑える。リスト項目は blur なしの半透明で代替し、blur は主役の要素のみに使う |
| **表紙画像の CORS**（実地検証済み） | cover.openbd.jp も Google の表紙も **CORS ヘッダを返さない**ため、`fetch()` → Blob 保存はそのままでは不可。表示は `<img>` 直参照で行い（CORS 不要）、Blob 保存は CORS を返す経路（画像プロキシ wsrv.nl は確認済み・楽天画像ホストは要実機確認）から取れた場合のみ。**SW の no-cors キャッシュは使わない**（Chrome は不透明レスポンス 1 件を約 7MB 相当としてクォータ計上する）。最後の砦はタイトルから決定的に生成するグラデーション表紙 |
| **書誌データの多段フォールバック**（実地検証済み） | ① openBD（CORS ◎・キー不要。ただし 2023-06 以降、表紙・内容紹介は版元ドットコム会員社のみ）→ ② NDL サーチ OpenSearch（CORS ◎・キー不要・和書の書誌は最強。XML）→ ③ 楽天ブックス（無料 applicationId 必須・表紙 URL の質は最良）→ ④ Google Books（**API キー必須**: キーなし利用は匿名共有枠のクォータが 0 で常に 429。リファラ制限＋Books API 限定のキーなら公開サイト埋め込みが標準運用）→ ⑤ 手入力 |
| **初回描画のちらつき** | データは全て IndexedDB からの非同期読みなので、初回描画はスケルトンを出す（純 SPA なので SSR/ハイドレーション不一致の問題自体が存在しない） |
| **同期ワーカーの CORS 設定ミス** | 症状が「同期だけ黙って失敗」になり気づきにくい。Phase 3 の最初に OPTIONS 応答を含む疎通テストを書く |
| **直リンクの初回 404** | 404.html フォールバックで表示は復元されるが HTTP ステータスは 404（Pages の仕様で変更不可）。個人用 PWA では実害なしと判断し受容 |
| **オリジン共有** | `kazuyan38.github.io` は同アカウントの全 Pages プロジェクトと同一オリジン。IndexedDB の名前空間・ストレージクォータ・`persist()` 許可を共有するため、DB 名は固有名にする。将来別アプリを Pages に置くときはこの点を思い出すこと |
| **iOS でのデータ永続性** | ホーム画面追加した PWA は 7 日削除ルールの対象外（WebKit 公式・確認済み）だが、ポリシーであって API 保証ではない。`storage.persist()` を初回書き込み時に呼び、真の保証は同期＋JSON エクスポートに置く |
| **アルゴリズムの後戻り** | ReviewLog を不変ログとして全件保持。将来 FSRS へ移行する際、履歴から全カードの状態を再計算できる |
